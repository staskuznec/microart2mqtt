# microart2mqtt

Показания инверторов **МикроАрт** в **MQTT**. Два варианта — под ваш случай:

- **Агент на «Малине»** (`cmd/malina-agent`) — крутится на самом устройстве,
  берёт данные из локального `read_json.php` и публикует в брокер. Ничего
  внешнего не нужно, у каждого инвертора свои топики, веб-настройка встроена в
  агент. **Основной путь.**
- **Центральный демон** (`cmd/microart2mqtt`) — стоит на отдельном сервере и
  опрашивает «Малины» по сети. Удобен, если прошивку трогать не хочется.

Оба публикуют в один брокер, дальше показания забирает кто угодно — умный дом,
Grafana, бот. В связке с
[mqtt2mimismart](https://github.com/staskuznec/mqtt2mimismart) они попадают в
MimiSmart и становятся обычными датчиками.

```
на устройстве:  «Малина» inv1 ── malina-agent ──MQTT──┐
                «Малина» inv2 ── malina-agent ──MQTT──┼──>  брокер
                «Малина» inv3 ── malina-agent ──MQTT──┘

централизованно:  «Малины» ──HTTP──> microart2mqtt ──MQTT──>  брокер
```

## Агент на «Малине»

Публикует **всё**, что отдаёт малина — топики создаются сами, поля описывать не
нужно (как zigbee2mqtt/tasmota):

```
microart/inv1/map/_UNET            231.0
microart/inv1/bat/0/C_100_remain   88.0
microart/inv1/mppt/0/P_PV          1450
microart/inv1/map                  {…весь JSON раздела…}
microart/inv1/availability         online | offline
```

В брокер уходят только изменившиеся значения; раз в `republish_sec` — весь
набор заново. Брокер, корень топиков, интервал и вкл/выкл — на встроенной
веб-странице агента (`http://<ip>:8091/` или кнопка **MQTT** в веб-морде малины).
**Весь интерфейс внутри бинарника**, PHP нет: обновили агент — обновился и веб.

**Обновление** — кнопкой на той же странице: агент качает свежий бинарник с
GitHub, сверяет SHA256, проверяет запуск и перезапускается; прежняя версия
остаётся для отката.

Развёртывание (одна прошивка, дальше только браузер) — см.
[docs/agent-malina.md](docs/agent-malina.md): образ патчится
`tools/malina_bootstrap.py` (консоль + автозапуск), бандл из `deploy/malina/`
вместе с собранным `malina-agent` кладётся на раздел `/boot` (виден в macOS), при
загрузке агент ставится сам. SSH прошивка МикроАрт не даёт — он и не нужен.

## Установка

Одной строкой на сервере, где стоит панель умного дома:

```sh
curl -fsSL https://github.com/staskuznec/microart2mqtt/releases/latest/download/install.sh | sudo sh
```

Установщик скачает бинарник под вашу архитектуру, сверит контрольную сумму,
заведёт службу systemd и спросит две вещи:

- **открыть управление рядом с панелью** — тогда оно будет доступно по
  `http://сервер/microart/`, а не отдельным портом;
- **добавить вкладку «Инверторы»** в меню MimiSetup.

Дальше — три шага в браузере:

1. **Настройки** → адрес MQTT-брокера.
2. **Инверторы** → «Добавить инвертор». Адрес «Малины» тот же, что открывается
   в браузере. Галочка «сразу добавить стандартный набор метрик» включена —
   получите заряд, ток, сеть, нагрузку, солнце и режим без ручной работы.
3. Готово. Показания пошли в топики.

### Обновление

Тем же самым:

```sh
curl -fsSL https://github.com/staskuznec/microart2mqtt/releases/latest/download/install.sh | sudo sh
```

База с настройками, инверторами и метриками лежит отдельно
(`/var/lib/microart2mqtt`) и не трогается. Прежний бинарник сохраняется рядом —
откат в одно движение, команду скрипт напечатает сам, если новая версия не
поднимется.

Демон раз в сутки проверяет, не вышла ли новая версия, и говорит об этом на
странице «Обзор». Сам себя он не подменяет: устройство, которое снимает данные
с инверторов, не должно менять свой бинарник посреди дня без спроса.

### Без установщика

```sh
make build-armv7                      # или make build под текущую платформу
scp exe/microart2mqtt-armv7 root@сервер:/opt/microart2mqtt/microart2mqtt
scp deploy/microart2mqtt.service root@сервер:/etc/systemd/system/
ssh root@сервер 'systemctl daemon-reload && systemctl enable --now microart2mqtt'
```

Вкладку в панель тогда придётся подключить руками: положите
`deploy/mimisetup-microart-tab.js` рядом с `index.php` панели под именем
`microart-tab.js`, поправьте в нём `DAEMON_URL` и добавьте после подключения
`app.js` строку:

```html
<script type="text/javascript" src="microart-tab.js"></script>
```

## Топики

```
microart/bridge/availability   online | offline   ← ставит брокер по LWT, если демон умер
microart/bridge/state          {"version":"1.0.0","uptime_sec":3600,"inverters":3,...}

microart/inv1/availability     online | offline   ← ставит демон по результатам опроса
microart/inv1/state            {"soc":88,"grid_voltage":231,"status":4,"ts":"..."}
microart/inv1/battery/soc      88
microart/inv1/grid/voltage     231
microart/inv1/load/power       820
```

Корень (`microart`), имена инверторов и хвосты топиков задаются в вебе.

Всё публикуется с `retain`, поэтому подписчик, подключившийся позже, сразу
получает последние значения, а не ждёт следующего опроса.

Про доступность стоит знать одну тонкость: **LWT в MQTT один на соединение**, а
соединение у демона общее на все инверторы. Поэтому `bridge/availability`
отдаётся брокеру как «завещание» — он разошлёт `offline`, если демон умрёт
целиком, — а доступность каждого инвертора демон выставляет сам по результатам
опроса. В сумме видно и то, что мост жив, и то, какая именно «Малина» отвалилась.

## Разделы интерфейса

**Обзор** — состояние брокера, время работы, сколько инверторов на связи и
последние значения по каждому. Здесь же появляется сообщение о новой версии.

**Инверторы** — список: добавить, править, временно выключить опрос, удалить.
Выключенный инвертор остаётся в списке со своими метриками, но не опрашивается.

**Метрики инвертора** — что именно публикуется. Метрику можно добавить
четырьмя способами:

- **из API** — самый удобный. Демон ходит на «Малину» и показывает **всё, что
  она отдаёт прямо сейчас, вместе с текущими значениями**. Отмечаете нужные
  строки — они становятся метриками. Уже добавленные помечены, чтобы не плодить
  дубли;
- **стандартным набором** — двенадцать обычных для МАП значений;
- **копированием с соседнего инвертора** — когда их несколько и они одинаковые;
- **вручную** — если знаете путь поля.

**Настройки** — брокер (адрес, логин, пароль, QoS, ретейн, TLS) и общие
параметры опроса. Сохранение перезапускает опрос сразу, перезагружать демон не
нужно.

**Журнал** — последние 500 записей с фильтром по уровню. Демон работает службой,
и причину неполадки видно не выходя из браузера.

## Откуда берутся данные

HTTP-интерфейс «Малины», без пароля (описан в документации МикроАрт, стр. 10–12):

| Источник | Запрос | Что внутри |
|---|---|---|
| `map` | `read_json.php?device=map` | состояние МАП: `_UNET`, `_PNET`, `_PLoad`, `_Status_Char` и остальное |
| `bat` | `read_json.php?device=bat` | батарейный монитор: `minute_data` (раз в минуту), `second_data` (раз в секунду) |
| `mppt` | `read_json.php?device=mppt` | контроллеры КЭС, массив с индексами 0–3 |

Путь к полю пишется через точку, индекс массива — числом:
`minute_data.C_100_remain`, `mppt_controllers.0.I`.

За один цикл каждый ответ забирается **ровно один раз**, сколько бы метрик из
него ни читалось. На три инвертора с двенадцатью метриками это шесть запросов в
полминуты — «Малина» такого не замечает.

Чаще пяти секунд опрашивать смысла нет: сама «Малина» усредняет данные с этим
шагом, а `minute_data` обновляется раз в минуту. По умолчанию стоит 30 секунд.

У «Малины» есть ещё SNMP v2c на чтение и трапы по авариям, но через HTTP-API
данных больше — все параметры плюс расчётные, — поэтому опрос идёт по нему.

## Что демон делает сам

**Шлёт только изменившиеся значения.** Раз в `republish_sec` (по умолчанию
10 минут) уходит полный набор — на случай, если подписчик или брокер потеряли
состояние. Если публикация не прошла, значение **не** считается отправленным и
уйдёт в следующем цикле: иначе топик остался бы пустым до планового рефреша.

**Переживает недоступный брокер.** Стартует, даже если брокера ещё нет, и
переподключается сам. После восстановления связи отправляет все значения
заново — ретейн на перезапущенном брокере мог не сохраниться.

**Не публикует пустоту.** Поля, которых «Малина» не прислала для своей
конфигурации, пропускаются: пустое значение в ретейн-топике хуже, чем прежнее.

**Помечает мёртвые инверторы.** После нескольких неудач подряд —
`availability=offline`. Остальных инверторов это не касается: у каждого своя
горутина, и зависший не мешает соседям.

**Разносит опросы по времени.** Десять «Малин» не дёргаются одновременно:
старты равномерно размазаны внутри интервала.

**Корректно останавливается** по SIGTERM: дожидается циклов опроса и выставляет
`offline` перед выходом.

## Почему один демон, а не по одному на инвертор

Инверторов может быть один, а может десять. Соблазн запустить по процессу на
каждый есть, но:

- одно соединение с брокером вместо N — меньше сессий, client_id и реконнектов;
- ~15 МБ памяти на любое число инверторов вместо 10 МБ на каждый;
- один конфиг, один unit, одно место с логами: добавить инвертор — строчка в
  вебе, а не новый unit-файл и новая строка в кроне;
- общий шедулер, который разносит опросы по времени.

Изоляция сбоев, ради которой обычно берут процесс на устройство, здесь решается
дешевле: у каждого инвертора своя горутина с `recover()`, зависший HTTP-запрос
отсекается таймаутом, а мёртвая «Малина» не мешает остальным.

## Устройство проекта

```
cmd/microart2mqtt/   точка входа: флаги, запуск, остановка
internal/
  app/               связывает хранилище, брокер и опрос; перенастройка на лету
  store/             SQLite: настройки, инверторы, метрики, миграции
  microart/          HTTP-клиент «Малины» и разбор ответов API
  mqtt/              клиент брокера: подключение с LWT, публикация, топики
  poller/            опрос одного инвертора и фильтр изменений
  web/               веб-интерфейс: страницы и формы
  update/            проверка новой версии
  logging/           журнал: stdout плюс кольцевой буфер для страницы
deploy/              unit systemd и вкладка для панели MimiSetup
install.sh           установка и обновление на объекте
```

Конфигов на диске нет: рядом с бинарником только файл базы, всё остальное
вводится в вебе. База открывается с правами 0600 — внутри пароль к брокеру.

SQLite взят чистый на Go (`modernc.org/sqlite`), без cgo, поэтому сборка под
ARMv7 ничем не отличается от сборки под хост.

### Разработка

```sh
make run     # локальный запуск, база в ./exe, веб на 127.0.0.1:8081
make test    # gofmt, go vet, go test -race, проверка install.sh
make deploy HOST=192.168.20.218   # выкатить свою сборку на объект, минуя релиз
```

### Релизы

Сборка идёт по тегу `v*`: GitHub Actions гоняет проверки, собирает три
архитектуры, считает контрольные суммы и прикладывает к релизу бинарники,
`install.sh`, unit и файл вкладки. Описание релиза берётся из сообщения тега —
пишите его осознанно.

```sh
git tag -a v1.0.0 -m "Что и зачем изменилось"
git push origin v1.0.0
```
